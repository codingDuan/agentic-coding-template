# 上线步骤：八个维度

计划（`writing-plans`）、执行（`executing-plans`）、PR 交接（`pr-ready`）共用这一份。
三处都只指向本文，不要各自复制一份。

兼容性矩阵回答「哪些调用方要改」，上线步骤回答另一个问题：
**「哪些正在运行的进程加载了这段代码，各自需要什么才能拿到新版本」**。
只写了批次顺序和回滚的计划，没有回答这个问题。

**逐项列出，没涉及的写「无」，不要省略行。**

> 模板说明：下表的维度名按实际部署形态改写（例如没有小程序就删掉那一行、多一个常驻进程就加一行），
> 但「每行必须回答」的要求保留。

| 维度 | 必须回答 |
|---|---|
| 数据库迁移 | 迁移 revision id；是否必须先于代码上线；是否只改数据、是否可逆 |
| API | API 进程是否需重启；相对其他组件的顺序与原因 |
| Worker / 后台任务 | 每一个后台进程各自是否需重启（见下方 import 依赖） |
| MCP / Agent | MCP / Agent 服务是否需重启（见下方 import 依赖） |
| Web | 是否需构建部署；其他端依赖的静态资源 |
| 小程序 / 应用商店类客户端 | 是否需发版/审核；审核周期；老版本对新 API 是否仍正确 |
| Mobile | 是否需 App 发版；老版本对新 API 是否仍正确 |
| 配置项 | 新增/变更的 env var、默认值、不设置能否正常部署（参考 `.env.example` diff） |

然后写明 **发布顺序**（跨维度的先后 + 原因）和**部署前/部署后验证**（只读 SQL、smoke 命令、要打开的页面、要切的开关）。
每个 PR 描述都写 **回滚/恢复**；普通改动一行即可（如「revert 本 commit 重新发布，无持久化数据变化」）。
迁移、支付、订阅、权限、通知、调度必须逐批说明回滚方式与**数据影响**，
包括不对称的情况（代码可回滚但已写入的数据不会自动还原）。

## 后台进程的 import 依赖（最容易填错的行）

后台进程（Worker、MCP、Agent）如果**直接 import 后端模块**而不是通过 HTTP 调 API，
那么「我只改了 API 目录」**推不出**它们不受影响。必须跑 import grep：

```bash
grep -rn "{{BACKEND_PACKAGE}}" {{WORKER_DIR}} --include='*.py' | grep -v build/lib
grep -rn "{{BACKEND_PACKAGE}}" {{AGENT_DIR}} --include='*.py' | grep -v build/lib   # 判断运行时耦合时排除 /tests/
```

再看命中的模块是否在本次 diff 里。漏掉的后果是这些服务继续跑内存里的旧代码，与 API 行为不一致。

⚠️ **`--include` 必须加引号。** 不加引号的 `--include=*.py` 会被 zsh 展开报错。

## 一个进程 ≠ 一个队列

如果有多个 Worker 进程消费不同队列，**每个进程都要单独回答是否重启**。
判断某个任务落在哪个进程，查任务路由定义，不要靠模块路径猜。

## 数据迁移的不可逆性

- 迁移执行一次后被记为「已执行」，**不会自动重跑**。如果迁移带前提条件（例如依赖某个配置值），
  上线前必须核对前提，并写清楚「前提不满足而跳过」时的恢复步骤。
- 回填类迁移要在日志里输出**被改动对象的 id 清单**，作为事后核对与手工回退的依据。
