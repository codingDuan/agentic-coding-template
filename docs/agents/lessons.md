# 合并后复盘教训

代码大量由 agent 编写和评审。定时任务（或手工）复盘前一天合入 `main` 的 PR：
哪些修了刚合入的东西、哪些不该那样合、哪些验证得太薄。学到的东西记在这里。
**改代码前读一遍。**

每条教训是一条规则，然后是为什么，然后是证据。「出现」统计的是在多少个不同日期被复盘到。
出现 ≥3 天，或只出现一次但代价高（资损、生产/预发不可用、错误数据写入生产、权限越界），
会在每周 fold 时沉淀进 `RULES.md`、模块 README 或对应 skill，并移到文末「已沉淀」。

机制与筛选标准见 `skills/pr-lessons/SKILL.md`。

> 模板预置：下面「教训」里标「源项目」的条目来自模板的来源项目，与技术栈无关，开工就值得知道。
> 它们**不计入**本项目的出现天数；本项目第一次复盘到同类问题时，补上本项目的证据，从 1 天开始计数。
> 与项目无关的条目可以直接删。

## 教训

### 测试与验证

**测试里显式钉住配置开关，不依赖本地 `.env`**
- 为什么：CI 没有 `.env`，开关回落到默认值；本地 `.env` 打开的开关会让测试在本地绿、在 CI 红，或者反过来掩盖缺陷。
- 源项目：多次出现「本地全绿、CI 失败」，根因都是测试默默读到了本地 `.env` 里的开关。
- 出现：源项目预置

**时间相关的测试同时冻结时钟和时区**
- 为什么：「当天 15:00 截止」这类闸门按服务器时区计算；开发机在别的时区、或在夜里跑，测试会随机失败。
- 源项目：发布前置检查在美西夜间运行时固定挂掉 10 个通知测试，修复是冻结时钟并钉住时区。
- 出现：源项目预置

**在 worktree 里验证时，确认测到的是 worktree 的代码**
- 为什么：可编辑安装（editable install）的包路径、已经在跑的 dev server 都指向主 workspace；不改 `PYTHONPATH` / E2E base URL 端口，测到的是主分支的旧代码。
- 源项目：worktree 里的测试和 Playwright 都「通过」了，实际加载的是主 workspace 的代码。
- 出现：源项目预置

**说「本地无法复现生产数据库问题」之前，先检查容器能不能起**
- 为什么：生产等价数据库的门禁大多能用一次性容器在本机复现；跳过它，「本地绿」对生产行为没有任何信息量。
- 源项目：几次把生产数据库门禁失败判成「本地无法复现」，实际 Docker 已安装、只是没启动。
- 出现：源项目预置

**推翻一个已确认的机制之前，至少复跑两次**
- 为什么：一次观察可能是缓存、端口占用或时序造成的偶然结果；据此改掉正确的约定，代价比多跑一次大得多。
- 源项目：一次实测「推翻」了客户端 E2E 的配置真相源，几天后复跑证明原结论是对的。
- 出现：源项目预置

### 迁移与数据

**带迁移的分支，推送前跑完整门禁并搜「上一个 head」**
- 为什么：新增迁移会让写死上一个 migration head 的测试失效；`test-critical` 不一定覆盖它们，CI 额度也比本地时间贵。
- 源项目：多次在 CI 上才发现写死旧 head 的测试失败。
- 出现：源项目预置

**按区间替换数据时，先校验新数据覆盖了整个区间**
- 为什么：「先删区间再写入」遇到上游缺数据时，会把真实记录删掉、只留下缺口或占位值，下游计算随之出错。
- 源项目：一次按区间替换的归档删掉了真实交易日、写入了占位价，几天后拖垮了两个依赖它的计算。
- 出现：源项目预置

### 评审与发布

**发布要重启哪些组件，以发布工具的分类为准，不凭判断**
- 为什么：发布脚本、部署工具本身的改动会影响所有后端进程；「我只改了 API 目录」不是证据。
- 源项目：改了发布脚本却写「无需重启」，实际发布工具判定为全部后端重启。
- 出现：源项目预置

**运行时写盘的路径落在共享目录，并且和反向代理配置一起核对**
- 为什么：不可变发布（每次发布一个新目录）下，写进发布目录的文件下次发布就会消失，运行用户也常常没有写权限；静态文件还要反向代理配置指向同一目录才能访问到。
- 源项目：后台生成的静态页写进发布目录，权限不足并且发布后丢失；修复后又发现 nginx 没有指向新目录。
- 出现：源项目预置
