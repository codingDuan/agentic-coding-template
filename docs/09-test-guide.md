# 测试指南

> 模板说明：本文回答两个问题——「改了什么，最少要跑哪些测试」和「怎样的结果才算证据」。
> 第 1、2 节是通用原则，保留；第 3、4 节按项目技术栈填写。

## 1. 证据原则

- 只报告有直接证据支持的结果；实现、测试、评审、部署、生产状态分开陈述。
- 「本地绿」不等于「生产等价」：凡是 `RULES.md` §1 列出的环境差异，必须在生产等价环境上验证。
- 开关类配置要在测试里**显式钉住**（如 `monkeypatch`），不能依赖本地 `.env`——CI 没有 `.env`，开关会回落默认值。
- 支付、订阅、权限、通知、认证、交易执行和数据迁移不能只靠纯函数单元测试，至少需要 API 或集成层验证；
  影响用户界面时补对应端 E2E / smoke，不能自动化的部分写清原因和人工步骤。

## 2. 迁移与失败处理

数据库迁移还要满足：

- 只有一个迁移 head；
- 在生产等价数据库上运行 upgrade；
- 回填或数据修正必须在有代表性数据的库上验证产物（`RULES.md` §4.1）；
- 新增迁移后，搜索把「上一个 head」写死的测试并同步更新。

测试失败时先保留原始命令和首个有效错误，再缩小复现范围。不要通过删除断言、扩大重试、跳过用例让结果变绿。
如果确认是既有失败（例如与时区、测试顺序相关的 flaky），要提供能复现它不由本分支引入的对照证据。

| 路径 | 最低要求 | 高风险时扩大到 |
|---|---|---|
| {{BACKEND_PATH}} | `{{BACKEND_TEST_COMMAND}}` | `make test-critical` + 全量 |
| {{WEB_PATH}} | `{{WEB_UNIT_COMMAND}}` + 相邻 E2E | 用户主流程 E2E |
| {{MIGRATION_PATH}} | 迁移单测 + 生产等价库 upgrade | 全量 + 生产等价库测试套件 |
| `skills/**` | skill 自带脚本的测试 | — |
| `docs/**` | 无 | — |

## 4. 常用命令（项目填写）

```bash

make test-critical              # 核心测试
{{FULL_TEST_COMMAND}}           # 全量
{{PROD_EQUIVALENT_DB_TEST}}     # 生产等价数据库测试
```
