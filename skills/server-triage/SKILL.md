# 线上问题排查（骨架，按项目填写）

> 模板说明：这是从实战项目提炼的骨架。**铁律和流程保留原样**，`{{...}}` 占位符和「项目填写」区块
> 在初始化项目后按实际基础设施填写。填完删除本说明。

## 铁律：服务器只读

**在服务器上只允许读操作。** 这不是建议，是硬约束：

- ❌ 禁止任何文件写入 / 修改 / 删除（含 `>`、`>>`、`sed -i`、`tee`、`touch`、`rm`）
- ❌ 禁止 SQL 写入（`INSERT` / `UPDATE` / `DELETE` / `ALTER` / DDL），只允许 `SELECT`
- ❌ 禁止重启服务、`kill`、执行迁移命令
- ❌ 禁止修改 crontab、反向代理配置、`.env`
- ❌ 禁止缓存/队列写命令，只允许读命令
- `.env` 只允许读取连接数据库/队列所需的键，禁止读取或展示其他键值（token、密钥）
- 发现需要写操作才能修复的问题 → **停下来，把结论和建议的操作命令告诉用户，由用户决定执行**

## 先查再断言

1. 排查生产问题前，先 `git log --grep` 搜历史修复，再**确认线上实际部署的版本**，不要拿本地 HEAD 推断线上行为。
2. 连接失败（SSH、权限、网络）时**立即停止远程排查**，结论写「远程验证不可执行 / 待有权限者验证」，
   把精确的只读命令交给有权限的人，列明需要返回的字段。不要从连接失败推断服务状态。
3. 服务器只做数据/日志的**抽取**，分析拉回本地做（落到 scratchpad，不在服务器写文件）。

## 数据库只读兜底

- 只读会话必须在**第一个语句**开启，并让客户端遇错即停（psql：`-X -v ON_ERROR_STOP=1` +
  `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY;`）。否则兜底失败时客户端会带着可写会话继续执行。
- 用 `SHOW transaction_read_only` 之类的**读语句**确认兜底生效，**不要用写语句去探测**。
- 应用配置里的连接串常带引号和 ORM 驱动后缀（如 `postgresql+psycopg://`），喂给原生客户端前先清洗。

## 常见症状 → 第一落点

| 症状 | 第一落点 |
|---|---|
| 接口 5xx / 超时 | API 服务日志中的 ERROR / Traceback |
| 定时任务没执行 | 先读代码里的调度定义确认时刻；再**双向确认**：调度器派发记录 + 执行器成功记录 |
| 页面白屏 / 静态资源 404 | 反向代理配置 + 前端产物目录 |
| 数据异常 | 只读 SQL 复现 → 对照写入代码 → 判断是代码缺陷还是历史脏数据（RULES.md §4） |
| 服务反复重启 | 重启次数 + 重启前最后一条错误 |

## 输出

根因 + 证据（日志原文 / 数据行）+ 建议的修复动作（写操作留给用户执行）。
