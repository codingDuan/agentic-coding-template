# 具体问法

讲回和模拟飞行的每一道题都按本文出。

## 什么算太抽象

如果一道题不用改字就能拿去问别的计划，它就太抽象。下面这些都是：「解释 D2」「事实源是什么」
「数据怎么流转」「选错了会怎样」。这类题，背下 agent 的解释也能答对，所以证明不了理解。

## 一道题由三部分组成

1. **触发**：一个角色、一个入口、真实的输入值。入口写计划或代码里的真实名字，比如接口路径、
   任务名、回调、按钮。
   例：用户 1001 在 15:01 调 `GET /api/products/42/signals`；支付回调 `PAY20261120001` 第二次到达；
   定时任务 `daily_rebalance` 在 15:30 和 15:31 各跑了一次。
2. **事前状态**：只列跟这道题有关的行和字段，写成具体值，
   例如 `subscription.status='active', expires_at=2026-11-30`。无关字段不写。
3. **一个预测**：一件能拿代码核对的事。可以是返回值或状态码、某个字段之后的值、写了哪张表的
   哪一行，或者被哪个函数或哪一层拒绝。

## 出题规则

- 问预测（「之后 X 是什么值」），不问描述（「说说 X 怎么工作」）。
- 要考「为什么这样选」，就问：同一个输入，换成被否决的方案会得到什么。
- 用计划或代码里的真实名字：路径、函数、表、字段、枚举值。
- 重问时，在同一个案例上只改一个变量，比如订阅过期、回调重复、旧客户端少传新字段。这样新的
  回答考的还是同一个机制。
- 一条消息最多问三道题，并编号。
- 记录表的 `题` 列写案例的简称，比如 `D2 线索 L-88 成交后看板读哪`。

## 对照

| 抽象 | 具体 |
|---|---|
| 解释 D2 为什么以 `crm_followup_case` 为事实源。 | 运营在侧边栏把线索 L-88 标为「已成交」，然后刷新收入看板。看板这一行读的是哪张表的哪个字段？如果用被否决的方案（读 `leads.status`），此刻看板显示什么？ |
| 说说支付回调的数据流。 | 订单 `PAY20261120001` 的回调首次到达，当时 `orders.status='pending'`。按顺序说：① 哪个函数先收到；② 读了哪一行；③ 写了哪些字段、写成什么值；④ 微信收到的响应是什么。 |
| 重复回调会怎样？ | 同一个回调 3 秒后又到了一次，此时 `orders.status='paid'`。`subscriptions` 会不会多一行？是哪个判断或约束挡住的？ |
