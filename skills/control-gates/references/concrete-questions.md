# 具体问法

讲回和模拟飞行的每一道题都按本文出。

## 什么算太抽象

如果一道题不用改字就能拿去问别的计划，它就太抽象。下面这些都是：「解释 D2」「事实源是什么」
「数据怎么流转」「选错了会怎样」。这类题，背下 agent 的解释也能答对，所以证明不了理解。

## 一道题由三部分组成

1. **触发**：一个角色、一个入口、真实的输入值。入口写计划或代码里的真实名字，比如接口路径、
   任务名、回调、按钮。
   例：用户 1001 在 15:01 调 `GET /api/products/42/signals`；支付回调 `PAY20261120001` 第二次到达；
   定时任务 `daily_rebalance` 在 15:30 和 15:31 各跑了一次。
2. **事前状态**：只列跟这道题有关的行和字段，写成具体值，
   例如 `subscription.status='active', expires_at=2026-11-30`。无关字段不写。
3. **一个预测**：一件能拿代码核对的事。可以是返回值或状态码、某个字段之后的值、写了哪张表的
   哪一行，或者被哪个函数或哪一层拒绝。

## 出题规则

- 问预测（「之后 X 是什么值」），不问描述（「说说 X 怎么工作」）。
- 要考「为什么这样选」，就问：同一个输入，换成被否决的方案会得到什么。
- 用计划或代码里的真实名字：路径、函数、表、字段、枚举值。
- 重问时，在同一个案例上只改一个变量，比如订阅过期、回调重复、旧客户端少传新字段。这样新的
  回答考的还是同一个机制。
- 一条消息最多问三道题，并编号。模拟飞行的四步数据流追踪算一道题。
- 记录表的 `题` 列先写[题型](#题型)标签，再写案例的简称，比如 `[简答] D2 线索 L-88 成交后看板读哪`。

## 题型

题型由要考什么决定，不按题目难度分配。选择类题型只能看出负责人能不能认出答案，理解要求负责人
自己写出答案。所以默认题型是简答预测。它的答案只是一个值、一个 `表.字段`、一个状态码或一个
函数名，负责人不用写大段文字。

| 标签 | 题型 | 用在哪里 | 要求 | 判定 |
|---|---|---|---|---|
| `[简答]` | 简答预测 | 每个关键决策和 `必须人理解` 项的第一轮 | 只写一个预测值、字段、状态码或函数 | ✅ / ⚠️ / ❌ |
| `[单选]` | 单选，加一句理由 | 考被否决方案的题；沿图追踪一条路径 | 3–5 个选项，其中一个是 `以上都不对` 或 `图上没有这条路径`；干扰项取被否决方案的输出，或相邻的分支、状态 | 选项对但理由错记 ⚠️ |
| `[判断]` | 判断，答「错」时要改正 | 只改一个变量的重问；状态转移是否合法 | 答「错」时写出正确的值或路径 | 任一部分错都记 ❌ |
| `[多选]` | 多选（选出全部） | 哪些事件能离开某个状态；故障发生时哪些行已经落库 | 选出完整的集合 | 漏选或多选都记 ❌ |
| `[排序]` | 排序 | 时序图的步骤顺序，尤其是回调乱序到达 | 4–6 个打乱的步骤 | 任一步骤位置错都记 ❌ |

规则：

- 一道 `[单选]` 或 `[判断]` 答对不能让一个项通过。通过条件是：`[简答]` 或 `[排序]` 答对，
  或者同一机制的两道不同题型的变体都答对。
- 选项不能泄露答案。正确选项不能是唯一带真实名字的、最具体的或最长的。每轮都换一次选项顺序。
- 流程图、时序图和状态机：让负责人沿图追踪一个案例，不要问图上画了什么。优先考失败分支、
  边界分支和去掉一层保护后的案例，因为正常路径不理解也能认出来。选项直接用图上的节点、步骤或状态：
  - 流程图：用 `[单选]` 问某个输入最后走到哪个终点节点。
  - 时序图：用 `[排序]` 问步骤顺序，用 `[多选]` 问第 N 步失败时哪些写入已经落库。
  - 状态机：用 `[单选]` 问某个事件之后的下一个状态，用 `[判断]` 问某个转移是否合法，用 `[多选]`
    问哪些事件能离开某个状态。
- 答案要对照代码核对，不能只对照图。图和代码不一致，说明计划有缺陷，先改计划再判分。
- 负责人选了 `图上没有这条路径`，而代码里这条路径确实存在：在 `处理` 列记一条计划缺陷，先把
  漏画的分支补进图里再继续。

## 对照

| 抽象 | 具体 |
|---|---|
| 解释 D2 为什么以 `followup_cases` 为事实源。 | 运营在侧边栏把线索 L-88 标为「已成交」，然后刷新收入看板。看板这一行读的是哪张表的哪个字段？如果用被否决的方案（读 `leads.status`），此刻看板显示什么？ |
| 说说支付回调的数据流。 | 订单 `PAY20261120001` 的回调首次到达，当时 `orders.status='pending'`。按顺序说：① 哪个函数先收到；② 读了哪一行；③ 写了哪些字段、写成什么值；④ 微信收到的响应是什么。 |
| 重复回调会怎样？ | 同一个回调 3 秒后又到了一次，此时 `orders.status='paid'`。`subscriptions` 会不会多一行？是哪个判断或约束挡住的？ |
