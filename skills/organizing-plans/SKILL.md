# 整理计划文档

## 核心原则

把 `docs/plans` 当作执行与观察层，不当作已落地系统事实的第二个权威源。先按业务领域和主题聚类，再用代码、测试、迁移和 Git 历史判断状态；先迁移长期事实，再删除被覆盖的计划。

## 何时使用

- 日期型计划散落在 `docs/plans` 根层或同一功能拆成多个目录。
- 设计、implementation、task、review 文档互相矛盾或重复。
- 需要判断“已完成”“上线观察”“被替代”“仅供历史追溯”而不能只看文档状态。
- 需要把计划入口做成领域 README → 主题 README → 设计/实施/任务的渐进式结构。
- 某个主题已上线，要把 task 子文档压缩进主文档并删除（见「模式 B」）。

不要用本 Skill 重写产品 PRD、API 正文或数据模型正文；那些文件是需要被核对和更新的权威来源。

## 模式 A：领域整理

1. 读取 `AGENTS.md`、`RULES.md`、`docs/plans/README.md`、相关 `docs/NN-*.md`、`docs/api-contract/**` 和模块 README。
2. 只用 `git ls-files 'docs/plans/*.md' 'docs/plans/**/*.md'` 建立清单；先记录工作区状态，保护未跟踪文件和范围外改动。
3. 为每个源路径记录 `domain`、`topic`、`decision`、代码证据和目标/权威入口。不要按日期或文档自报状态批量删除。
4. 一级目录按业务领域组织，领域清单以 `docs/plans/README.md` 的「领域入口」表为准（例如 `billing`、`auth`、`notifications`、`governance`）。
5. 每个领域和主题建立 `README.md`。README 只写边界、状态、当前结论和权威链接；设计、实施、任务细节按需下钻。
6. 以核心业务状态选择跨领域主入口：哪个领域拥有该状态的写入方，就以它为主入口（例如订单/权益归 `billing`）；另一侧只链接，不复制状态机或契约。
7. 处置源文档：
   - 活跃或上线观察：迁入主题并明确未完成门槛。
   - 长期规则：先更新架构/API/数据模型/模块 README，再删除计划。
   - 被替代：合并仍有效结论，标明当前替代入口，再删除旧方案。
   - 历史价值：只保留不可从当前代码还原的架构决策、不可逆迁移、上线/回滚手册或事故防复发约束，放入 `_archive/<domain>/<topic>/`。
   - 已被完整覆盖：删除，依赖 Git 历史追溯。
   - 证据不足：保留，明确缺口，不猜测完成。
8. 更新当前 Markdown 导航；历史命令、提交记录和明确标注的旧路径可保留。不要创建旧路径跳转文件。
9. 每个领域完成后运行审计，再处理下一个领域。

## 模式 B：上线后 task 归档

由人点名一个主题发起。目标是删除只含执行细节的 task 子文档，把代码与 Git 还原不出的信息留在主文档。单主题不需要建领域账本。

1. **定位**：从主文档的子任务索引收集 task 文件，再用 `git ls-files <主题目录> | grep -i task` 兜底；索引漏列的文件一并报告。
2. **前置核验**，任一不满足就停止并列出缺口，不做部分归档：
   - 每个 task 都能对应到已合入 `main` 的 PR 或提交（`gh pr list --state merged --search <关键词>`，或 `git log main --oneline -- <task 列出的文件>`）；
   - 主文档和主题 README 没有未关闭的「上线观察」「生产门槛」「待开始」「进行中」「待手工验证」；
   - 是否已上线由发起人确认：当前发布不打 `v*` tag，无法从 Git 判断；有疑问时用 `server-triage` 查生产部署版本。确认前不做归档。
3. **先迁长期事实**：task 里的长期契约、状态机、硬约束按模式 A 第 7 步写入权威文档，不塞进主文档。
4. **回填主文档**：优先填已有的「实际改动清单」「踩坑记录」节；没有时在文末追加 `## 实施结果（YYYY-MM-DD 归档）`。每个 task 一行：

   | Task | 结果 | 落点文件/模块 | PR / 提交 | 偏离原计划 | 遗留 |
   |---|---|---|---|---|---|

   只写偏离原因、放弃的方案、踩坑和遗留项；代码片段、命令、步骤清单一律不搬。「PR / 提交」列以 `main` 上的提交为准：squash 合入后，task 里记录的分支提交不在 `main`，照抄会留下删分支后即失效的引用。
5. **改写索引**：子任务链接改为纯文本并标注「已归档（YYYY-MM-DD）」。
6. **删除**：`git rm` task 文件和空的 `tasks/` 目录；不建跳转文件，不移入 `_archive/`。
7. **审计**：运行下方快速检查（单主题可省略 `--ledger` 和 `--base-ref`；与改动前输出比对，不新增违规即可），修复 `DANGLING_DOC_REF` 与失效链接，再更新主题 README 状态。

## 快速检查

```bash
python skills/organizing-plans/scripts/audit_plans.py \
  --repo-root "$PWD" --check \
  --ledger /tmp/plan-organization/disposition.tsv \
  --base-ref "$BASE_REF"
```

脚本只做确定性检查：领域目录是否已注册、领域/主题 README、Markdown 相对链接、`docs/plans/...` 仓库路径、**非 Markdown 文件里的文档引用是否可达**、账本一一对应、已提交改动范围。根层文件不拦——新增计划的落点口径以 `RULES.md` 和 `writing-plans` skill 为准。

`DANGLING_DOC_REF` 覆盖源码注释、测试 docstring、CI workflow 和 dev 脚本里的 `docs/plans/...` 指针。这类引用不参与构建，失效时 lint 和 CI 都不会红，历史上已因此悄悄烂掉四次；移动或删除计划文档后必须跑一次本检查，不能靠人工记得排查。它不自动判断业务语义；语义必须由代码证据支持。

完成前还要执行 `git diff --check`、`git status --short`，并按受影响路径运行项目规定的测试；先运行 `make test-critical-scope`，按 `RULES.md` §8 决定是否需要 `make test-critical`，并贴出输出。

## 常见错误

| 错误 | 修复 |
|---|---|
| 把“生产门槛待满足”写成已完成 | 保留上线观察状态，列出迁移、PostgreSQL、真机、支付或开关门槛 |
| 用日期决定归档 | 读取实现、测试、迁移和 Git 提交；无法确认就保留 |
| 在两个领域各留一份状态机 | 按核心业务状态选一个主入口，另一侧只链接 |
| 移动后只检查总 README | 检查主题内设计/实施/task 链接、绝对仓库路径和锚点 |
| 归档区堆放所有旧文档 | 普通历史依赖 Git；只保留不可还原的决策、迁移、runbook 或事故约束 |
| 直接编辑 `.codex/skills` 或 `.claude/skills` | 只改 `skills/`，最后运行 `bash scripts/install-skills.sh` |
| 只看 PR 已合入就归档，忽略上线观察门槛 | 前置核验不过就停，列出缺口交给发起人 |
| 把 task 的代码片段、命令搬进主文档 | 只写偏离原因、踩坑和遗留；细节靠 Git 追溯 |
| 另建 summary 文件或把 task 移进 `_archive/` | 回填主文档已有节后直接 `git rm` |

## 结果记录

在治理实施计划中回填每批保留、移动、删除、权威文档更新数量和证据缺口。若发现当前计划与代码冲突，先修正文档状态或权威来源，再继续移动；不要静默覆盖实现事实。
